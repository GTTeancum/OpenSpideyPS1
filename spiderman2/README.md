# Spider-Man 2: Enter Electro (USA, SLUS-01378) — native recompilation

A [RecompOne](https://github.com/BlackLabelHQ/RecompOne) port of the PlayStation
Spider-Man 2: Enter Electro (Vicarious Visions, 2001), built from the retail USA
Rev 1 disc following `../RECOMP-PLAYBOOK.md`.

**State: boots and plays through to the first level.** Logos, both intro movies, the
title screen, the main menu, difficulty select, the level cinematic and the Daily Bugle
headline all render; NEW GAME reaches episode 1 mission 0 and holds live gameplay for
over ten thousand frames with the HUD, pickups, physics and working controls. See
[TO_DO.md](TO_DO.md) for what is not verified.

---

## Layout

Two games share this repository, siloed by directory. Nothing here touches Spider-Man.

```
tools/RecompOne/          the recompiler and runtime, shared
spiderman2/
  config/
    spiderman2.json       generated by tools/mkconfig.py -- do not hand-edit
    funcmaps/             *_sweep.json are raw; the rest are derived
    overlays/             overlay images pre-relocated to their fixed bases
  extracted/              disc contents + CD.WAD entries (gitignored)
  patches/                hand-written C# the recompiled code calls into
  port/                   the .NET project
  generated/              recompiler output (gitignored)
  tools/                  the pipeline
```

## Building

Needs .NET 10, Python 3 with `numpy`/`PIL`, and the disc at the repository root for the
first extraction only.

```bash
cd spiderman2
python tools/disc.py extract extracted          # disc -> extracted/
python tools/cdwad.py extract extracted/wad     # CD.WAD -> extracted/wad/
python tools/overlays.py build config/overlays  # relocate the overlays
python tools/genmaps.py                         # linear-sweep maps (slow, once)
python tools/build.py                           # maps -> recompile -> closure -> build
```

`tools/disc.py` writes normal loose files, a `recompone-disc.json` LBA manifest, and
sector-preserving XA/STR files. `config/spiderman2.json`, the recompiler, and the built
port all read `extracted/` afterward; BIN/CUE is not a runtime dependency and can be
removed or archived after this first import. At runtime, CD.WAD lookups are served from
the individual files under `extracted/wad/` as well.

`tools/build.py` converges at **3,262 functions** across 29 modules with **9 residual
targets**, which are jump-table analysis running off the end of a real table into the
data after it — unreachable by any real path.

```bash
./port/bin/Release/net10.0/SpiderMan2.exe
```

## It is the same engine as Spider-Man, and that is the whole story of this port

Spider-Man was Neversoft's and Spider-Man 2 is Vicarious Visions', but the engine
carried across intact, and every hard-won piece of the first port applied unchanged:

- **`CD.HED` / `CD.WAD` parse byte-identically.** The same reader — name as a
  NUL-terminated string padded to a 4-byte boundary, then a u32 offset and a u32 length,
  offsets sector-aligned — reads this disc's index with no changes at all. 634 entries.
  The game's own reader is at `0x8006FC9C` and uses the same `(len + 3) & ~3` stride.
- **The overlay format is the same.** 28 `<name>.bin` / `<name>.rel` pairs, the
  relocation stream a flat u32 array terminated by `0xFFFFFFFF` with the type in the low
  two bits, and the same four types. **7,381 relocations decoded, every one landing on
  an instruction of the right kind, exact terminators, zero trailing bytes.** The game's
  relocator at `0x8001EEF0` matches `tools/overlays.py` instruction for instruction,
  including the quirk of adding `base` to the whole instruction word on a type 2 and
  masking afterwards.
- **Eight overlay names survive verbatim**: `chopper`, `hostage`, `lizard`, `mj`,
  `shell`, `thug`, `training`, `turret`.

So the pipeline was retargeted rather than rediscovered, and the port built and booted
on its first recompile.

### Carrying the hand-identified names across

The names that matter are not in the executable — they were recovered by hand for the
first port, and re-deriving them here would have been the bulk of the work.
`../tools/enginematch.py` moves them instead. It matches on **instruction shape** rather
than bytes: each word reduced to the part a relink cannot change — opcode, register
fields, and for SPECIAL the function code — with branch displacements, immediates and
the 26-bit target of `j`/`jal` dropped. What survives is the register allocation and
control flow the compiler produced, which is stable across a rebuild of the same source.

Nine names came across at **score 1.000** with a large margin over the runner-up:

| name | Spider-Man | Spider-Man 2 | words |
|---|---|---|---|
| `LoadOverlay` | `0x8001B990` | `0x8001E8E4` | 107 |
| `OverlayRelocate` | `0x8001BF58` | `0x8001EEF0` | 59 |
| `CdWadFind` | `0x80064B3C` | `0x8006FC9C` | 123 |
| `CdWadRead` | `0x80064D28` | `0x8006FE88` | 31 |
| `CdWadWait` | `0x80064F3C` | `0x800700A0` | 14 |
| `HeapAlloc` | `0x800651C8` | `0x8007032C` | 200 |
| `HeapFree` | `0x800654E8` | `0x8007064C` | 39 |
| `ModelFind` | `0x800694B8` | `0x8007463C` | 25 |
| `TriggerPass` | `0x8005DAE0` | `0x800685D8` | 92 |

**A score is not a verification.** Each was read at its new address before being trusted,
and `LoadOverlay` confirms most of them at once: it calls `CdWadFind`, `HeapAlloc`,
`CdWadRead` and `CdWadWait` twice — once for the image, once for the `.rel` stream —
then `OverlayRelocate`, then `HeapFree` on the relocation stream, then `jalr`s into the
overlay's first word. That is exactly the sequence the Spider-Man port documents.

The tool is deliberately in `../tools/` and takes both executables and the symbol file as
arguments. Nothing under `spiderman2/` reads anything under `spiderman/`; the transplanted
names live here as a committed `funcmaps/manual.json`, so this port builds on its own.

## Recovering the SDK symbols

The game statically links PsyQ, and RecompOne routes libgpu, libcd, libpad and
libcdstream to its runtime **by name**, so recovering those names is what turns raw
hardware access into host calls.

`tools/psyq_signatures.py` recovers **267 names, 192 uniquely placed**, including every
routing-critical one: `VSync`, `DrawOTag`, `DrawSync`, `PutDrawEnv`, `PutDispEnv`,
`ResetGraph`, `CdInit`, `CdRead`, `CdControl`, `CdSearchFile`, `StSetStream`,
`StGetNext`, `SpuInit`, `InitGeom`, `PadInitMtap`, `PadGetState`, `PadSetMainMode`.

The SDK libraries are **not** in this repository. Fetch the PsyQ 4.7 conversion
(`psyq-4.7-converted-full.7z`, from `psx.arthus.net/sdk/Psy-Q/`), extract it, and point
the script at its `lib/` directory:

```bash
python tools/psyq_signatures.py extracted/SLUS_013.78 80010000 <psyq>/lib \
       config/funcmaps/psyq_main.json
```

Code in the main executable ends at `0x8009D578` — `CD_getsector`'s `jr ra` is the last
instruction and pointer tables start on the very next word, which is what
`MAIN_TEXT_LIMIT` in `tools/fixmaps.py` is set from.

## Overlays

28 overlays, 500 KB, pinned at `0x80200000`–`0x8027D000`, which is why the port runs
with 8 MB of RAM rather than the retail 2 MB — the same reasoning as the Spider-Man
port, and safe for the same reason: `PSMemory` resolves RAM as `phys % ram.Length`, so
at 8 MB the overlay region is distinct storage the game never allocates from.

`patches/OverlayPatches.cs` redirects the game's own allocation to the same fixed base,
so the game's relocator produces byte-for-byte the image the recompiler was built from.

## Two fixes to the shared runtime

Both game-agnostic, both in `../tools/RecompOne/`, and **Spider-Man was rebuilt and
re-run afterwards to confirm it still reaches level 1 gameplay** — it does.

- **`CallRing._idx` overflowed.** It was an `int` incremented on every recompiled call.
  This game polls `StGetNext` while a movie plays — over a billion calls in a single
  run — so the index wrapped negative, and `Tail`'s `start < 0` clamp then took its
  count from a negative `end` and threw `OverflowException`. The effect was that the
  watchdog's stall dump broke exactly when a long run finally wedged, which is the one
  moment the ring exists for. It is a `long` now, and `Tail` clamps properly.
- **The stream ring had no way to say what it had done.** `LibCdStream` now counts
  frames queued and taken, empty `StGetNext` returns and skipped sectors, and exposes
  them as `RingState`. No behaviour change; it is what made the movie investigation
  below possible at all.

## Diagnostics

One log per run, `spidey.log`, written beside the executable and flushed as it goes.

```
SPIDEY_QUIET=1              turn the verbose game trace off
SPIDEY_TRACE_WAD=1          every archive lookup, frame-tagged
SPIDEY_TRACE_MOVIE=1        the movie player's frame, target and done flag
SPIDEY_HOT=8000,12000       the functions dominating the call ring on these frames
SPIDEY_TICK=800a4e2c        an address to read the simulation tick from, if one is found
SPIDEY_STALL=45             seconds without a frame before the watchdog dumps
SPIDEY_STALL_EXIT=1         exit rather than hang once it has dumped
SPIDEY_GUARD=800c1fd8       report writes to an address, with the call ring
SPIDEY_LENIENT=1            survive unmapped reads instead of throwing, and log them
SPIDEY_SNAP=crash           dump the game's RAM on the crash, or on named frames
```

`SPIDEY_HOT` earned its place immediately. A game that presents frames at full rate
while its state machine has stopped moving never trips the watchdog, and the picture
alone cannot say which loop it is in — naming the functions dominating the call ring
turned "it froze on the Daily Bugle screen" into "it is polling input, so it is waiting
for the player", which was the whole answer.

## Verifying

`patches/Capture.cs` reads frames back from the GPU backend, so a capture is what the
emulated console drew, not what the desktop showed.

```
SPIDEY_HZ=30               host presentation/GPU pacing budget; default 30 Hz
SPIDEY_LEVEL=e3m1          boot straight into a level (44 prefixes)
SPIDEY_CHEATS=all          the game's own cheats: everything, levels, costumes,
                           gallery, training, debug, bigfeet, bighead, whatif
SPIDEY_SHOTS=1050,title.bmr+450
                           write a PNG on an absolute frame or after an archive load
SPIDEY_SHOT_EVERY=200      ...or every N frames
SPIDEY_SHOT_DIR=shots      where they go
SPIDEY_EXIT=13000          quit after frame N
SPIDEY_SCRIPT=title.bmr+80:start:10
                           press a button N frames after an archive file loads
SPIDEY_ANALOG=0            present a digital pad instead of a DualShock
```

**This reaches level 1 from a cold boot** and is the run every screenshot here came
from:

```bash
SPIDEY_SCRIPT="title.bmr+80:start:10;title.bmr+280:cross:10;title.bmr+480:cross:10;\
title.bmr+700:cross:10;e1m0_t.trg+1200:cross:8;e1m0_t.trg+1500:cross:8;\
e1m0_t.trg+1800:cross:8;e1m0_t.trg+2100:cross:8;e1m0_t.trg+2400:cross:8" \
SPIDEY_SHOT_EVERY=200 SPIDEY_EXIT=13000 ./SpiderMan2.exe
```

Four presses walk the title screen, main menu and difficulty select; the rest dismiss the
level cinematic and the Daily Bugle headline, which **wait for the player by design** —
see TO_DO.md, because that cost real time to establish.

### Anchor a step to an archive load, not to a frame

The game paces off the wall clock, so the frame a screen appears on moves by hundreds
between runs. `title.bmr+80` means "80 frames after the title screen's archive loads",
which means the same thing every run. Two probe runs put `title.bmr` at frames 1810 and
1812; four put it at 1804–1856.

`name#2+400` anchors to the *second* load of a file. Some archives are read more than
once — the attract loop reloads `shell.bin` and `title.bmr` every cycle — so a step that
must mean the later one can say so. The same `name#N+offset` syntax works for
`SPIDEY_SHOTS`, so proof captures and scripted inputs share one deterministic clock.

### Two harness traps found here

- **An unresolved anchor pressed its button at boot.** A step waiting for its archive
  sits at frame `-1`, and the window `frame >= -1 && frame < -1 + hold` is open on
  frames 0..hold-2 — so *every* anchored script also pressed its button on frame 0.
  Here that skipped the intro movies, which meant a run with a script armed and a run
  without it were different runs, and frame numbers measured on one did not apply to the
  other. `title.bmr` loaded at frame 78 with a script and 1810 without.
- **The archive trace was the inverse of `SPIDEY_QUIET`.** That trace is what a script
  is written against, so measuring the load order cost a pile of console I/O that
  scripting it did not. It is `SPIDEY_TRACE_WAD` now, settable independently, so the
  measurement run and the scripted run can be the same run.
