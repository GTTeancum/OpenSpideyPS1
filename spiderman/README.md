# Spider-Man (USA, SLUS-00875) — native recompilation

A [RecompOne](https://github.com/BlackLabelHQ/RecompOne) port of the PlayStation
Spider-Man (Neversoft, 2000), built from the retail USA disc following
`../RECOMP-PLAYBOOK.md`.

**State: loads a level, dies on the first gameplay frame.** Logos, title screen, main
menu and difficulty select all render and respond to input; the intro FMV plays (badly).
Selecting a difficulty loads level 1 completely — trigger list, both actor code overlays,
actor models and the level geometry — and actors spawn. It then crashes in the object
renderer on the first gameplay frame. Runs at ~59 fps. See [TO_DO.md](TO_DO.md) for the
diagnosis and what has been ruled out.

## Layout

Two games share this repository, siloed by directory. Nothing here touches
Spider-Man 2.

```
tools/RecompOne/          the recompiler and runtime, shared
spiderman/
  config/
    spiderman.json        generated by tools/mkconfig.py -- do not hand-edit
    funcmaps/             *_sweep.json are raw; the rest are derived
    overlays/             overlay images pre-relocated to their fixed bases
  extracted/              disc contents + CD.WAD entries (gitignored)
  patches/                hand-written C# the recompiled code calls into
  port/                   the .NET project
  generated/              recompiler output (gitignored)
  tools/                  the pipeline
```

## Building

Needs .NET 10, Python 3 with `numpy`/`PIL`, and the disc at the repository root.

```bash
cd spiderman
python tools/disc.py extract extracted          # disc -> extracted/
python tools/cdwad.py extract extracted/wad     # CD.WAD -> extracted/wad/
python tools/overlays.py build config/overlays  # relocate the overlays
python tools/genmaps.py                         # linear-sweep maps (slow, once)
python tools/build.py                           # maps -> recompile -> closure -> build
```

`tools/build.py` runs the whole loop and stops when the unmapped-call count stops
falling. It currently converges at **3,314 functions** across 31 modules with
**17 residual targets**, which are jump-table analysis running off the end of a real
table into the data after it — unreachable by any real path.

Run it:

```bash
./port/bin/Release/net10.0/SpiderMan.exe
```

## The two things that made this game different

### CD.WAD, not a directory of files

The disc holds four files. Everything the game loads lives inside `CD.WAD` (63 MB),
indexed by `CD.HED`. A `CD.HED` record is the file name as a NUL-terminated string
**padded to a 4-byte boundary**, then a u32 byte offset and a u32 length, with offsets
sector-aligned. The variable-width name field is why a fixed-stride read of that table
falls apart a few hundred entries in — `sfx.vab` occupies 8 bytes of name and
`sp_tex00.psx` occupies 16. `tools/cdwad.py` reads it; the game's own reader is at
`0x80064B3C` and uses exactly the same `(len + 3) & ~3` stride.

### Relocatable overlays

The 30 code overlays are `<name>.bin` plus `<name>.rel`. `LoadOverlay` (`0x8001B990`)
looks the image up in CD.WAD, asks the heap for a block, reads it in, walks the
relocation stream patching it for wherever it landed, then calls its first word as an
init function.

The relocation stream is a flat u32 array terminated by `0xFFFFFFFF`. Each entry is a
byte offset with the type in the low two bits, which are free because every site is
word aligned:

| type | site | patch |
|---|---|---|
| 0 | a stored 32-bit pointer | `*site += base` |
| 1 | `lui` of a hi/lo pair | hi16 of `base + addend`; the addend is the **following u32** |
| 2 | the lo16 half | low 16 of `site + base` — its own immediate is the addend |
| 3 | `jal`/`j` | retarget the 26-bit field |

This decode was checked against all 30 overlays: 8,883 relocations, every one landing
on an instruction of the right kind, exact terminators, zero trailing bytes. The game's
own relocator at `0x8001BF58` matches it instruction for instruction.

**A static recompile cannot follow a heap address.** So every overlay is assigned a
fixed base of its own above the 2 MB the game's allocator knows about, the image is
relocated there ahead of time for the recompiler (`tools/overlays.py`), and at runtime
the allocation is redirected to the same address (`patches/OverlayPatches.cs`). The
game's own relocator then produces byte-for-byte the image the recompiler was built
from. 30 overlays, 628 KB, no overlaps.

That requires RAM larger than retail, so the port runs with 8 MB. This is safe
specifically *because* it is 8 MB: `PSMemory` resolves RAM as `phys % ram.Length`, so at
the retail 2 MB an address of `0x80200000` would alias back to `0x80000000` and land on
the game's own memory. At 8 MB it is distinct storage the game never allocates from.

An overlay image is never freed. `HeapFree` ignores anything in the region — the
pointer has no block header in front of it, so handing it to the allocator's free list
would corrupt the heap. Each overlay owns its region permanently, so there is nothing
to reclaim it for.

## Recovering the SDK symbols

The game statically links PsyQ 4.x (`$Id: sys.c,v 1.140 1998/01/12 ... $` is still in
the binary). RecompOne routes libgpu, libcd, libpad and libcdstream to its runtime
**by name**, so recovering those names is what turns raw hardware access into host
calls — it is the pivot of the whole port.

`tools/psyq_signatures.py` matches each library function against the executable as a
byte pattern with relocated fields masked, resolving ambiguities by cross-checking
relocation targets. Against the PsyQ 4.7 ELF conversion it recovers **248 names, 184
uniquely placed**, including every routing-critical one: `VSync`, `DrawOTag`,
`DrawSync`, `PutDrawEnv`, `PutDispEnv`, `ResetGraph`, `CdInit`, `CdRead`, `CdControl`,
`CdSearchFile`, `StSetStream`, `StGetNext`, `SpuInit`, `InitGeom`.

The SDK libraries are **not** in this repository. Fetch the PsyQ 4.7 conversion
(`psyq-4.7-converted-full.7z`, 1.5 MB, from `psx.arthus.net/sdk/Psy-Q/`), extract it,
and point the script at its `lib/` directory:

```bash
python tools/psyq_signatures.py extracted/SLUS_008.75 80010000 <psyq>/lib \
       config/funcmaps/psyq_main.json
```

`config/funcmaps/manual.json` pins the handful of game functions identified by hand and
verified by reading the code at each address — the overlay loader, the heap, the
archive reader, `PadInitMtap`, `SpawnActor`. Those names are the handles the patches in
`config/spiderman.json` attach to, so they matter beyond documentation.

## Fixes made to RecompOne

All game-agnostic; all in the shared checkout.

- **`CdInit` returned the wrong value.** libcd's `CdInit` returns **1** on success and
  0 on failure, the opposite of the usual convention. The runtime had it inverted, so
  the game's retry loop spun forever and never got past a black screen. Read it off the
  game's own statically-linked copy at `0x8008A16C`: it sets `v0 = 1` leaving the
  success path and only reaches `v0 = 0` after printing `CdInit: Init failed`.
- **Overlay images from a local file.** A new `path` on an overlay config (and `-path`
  on the sweep generator) reads the image from disk instead of the disc. A game that
  relocates an overlay while loading it has no byte range on the disc that matches what
  actually executes, so those bytes have to be prepared outside.
- **Register context on a failed dispatch.** `unmapped call: 0x00000000` says nothing
  about why. It now prints the argument and saved registers and the resident overlays,
  which is what turned that message into "the object pointer is null" and then into
  "the overlay was never loaded".

Carried over from the X-Men port and confirmed to matter here: the `MoveImage`
destination-register fix, jump tables that leave the function, the idle-loop breaker,
`VSync(-1)` advancing off the wall clock, and re-offering card completions.

## Diagnostics

One log per run, `spidey.log`, written beside the executable and flushed as it goes, so
there is exactly one place to look after a lock-up. It carries a frame-tagged trace of
overlay loads, actor spawns, archive lookups and trigger scripts, a watchdog that dumps
the CPU context and the tail of the call ring collapsed into runs when frames stop, and
a per-frame breakdown of present / throttle / game time.

```
SPIDEY_QUIET=1              turn the verbose game trace off
SPIDEY_LOG_STAMP=1          keep a timestamped log per run instead of overwriting
SPIDEY_STALL=12             seconds without a frame before the watchdog dumps
SPIDEY_GUARD=8009c5d4       report writes to an address, with the call ring
SPIDEY_GUARD_VALUE=00a402c7 report wherever this exact word gets stored
SPIDEY_LENIENT=1            survive unmapped reads instead of throwing, and log them
```

The recompiler has two matching switches: `"spAudit": true` in `config/spiderman.json`
checks that every function restores the stack pointer and the callee-saved registers,
and `"callRing": true` keeps the ring the watchdog prints.

## Verifying

`patches/Capture.cs` reads frames back from the GPU backend, so a capture is what the
emulated console drew, not what the desktop showed.

```
SPIDEY_SHOTS=1050,1500     write a PNG on these frames
SPIDEY_SHOT_EVERY=150      ...or every N frames
SPIDEY_SHOT_DIR=shots      where they go
SPIDEY_EXIT=2200           quit after frame N
SPIDEY_SCRIPT=1150:start:10;1400:start:10;1700:cross:10
```

Reaching the title screen and the difficulty menu:

```bash
SPIDEY_EXIT=2200 SPIDEY_SHOT_EVERY=150 SPIDEY_SCRIPT="1150:start:10;1400:start:10" ./SpiderMan.exe
```

Diagnostics (`patches/Diag.cs`) write one timestamped, frame-tagged log per run under
`logs/`, with a watchdog that dumps where the game was when it stopped.
`SPIDEY_TRACE_GAME=1` names every overlay load and actor spawn; `SPIDEY_TRACE_WAD=1`
names every archive lookup and whether it resolved. Those two are what located the
current blocker.

**The game paces off the wall clock, not the frame counter.** Two runs of the same
script diverge, and merely enabling logging changes where things land. Do not compare
two runs at the same frame number — capture a burst and match by content.
